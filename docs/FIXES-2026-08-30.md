## Issue 1: Calling Completely Broken

### Root Cause
`DialerScreen` passed an `onCall` callback that navigated to `"call-outgoing/$number"`, but this route was never registered in `Navigation.kt`. The `DialerViewModel.dial()` method existed but was never invoked. Additionally, `CallEngine.makeCall()` only created a database record and emitted events — it never launched a telephony intent to actually place the call.

### Impact
- Tapping the green call button on the dialer would crash or show a blank screen
- Contacts screen call button had the same issue
- API-initiated calls via `POST /v1/calls` would create records but never connect

### Files Changed

#### `platform/.../CallEngine.kt`
**Before:** `makeCall()` only created a DB record and updated state.
**After:** `makeCall()` creates the DB record, then calls `launchCallIntent()` which:
- Uses `ACTION_CALL` if `CALL_PHONE` permission is granted (places call directly)
- Falls back to `ACTION_DIAL` if permission is missing (opens dialer with number)
- Supports subscription ID for multi-SIM via `tel:` URI parameter

```kotlin
private fun launchCallIntent(phoneNumber: String, subscriptionId: Int? = null) {
    val uri = if (subscriptionId != null && subscriptionId > 0) {
        Uri.parse("tel:$phoneNumber?subscription=$subscriptionId")
    } else {
        Uri.parse("tel:$phoneNumber")
    }
    val action = if (hasCallPhonePermission) Intent.ACTION_CALL else Intent.ACTION_DIAL
    context.startActivity(Intent(action, uri).apply { flags = Intent.FLAG_ACTIVITY_NEW_TASK })
}
```

#### `ui/.../DialerScreen.kt`
**Before:** `onCall` parameter triggered navigation to non-existent route.
**After:** `onCall` parameter removed; call button invokes `viewModel.dial()` directly.

#### `ui/.../Navigation.kt`
**Before:** `DialerScreen` passed `onCall = { navController.navigate("call-outgoing/$number") }`.
**After:** `DialerScreen()` called with no `onCall` parameter. Contacts screen launches `ACTION_CALL` intent directly.

## Issue 2: Role Setup UI Never Refreshes

### Root Cause
`MainActivity` used `var showRoleSetup by remember { mutableStateOf(!roleManager.isFullyDefault()) }` inside `setContent`, but after the role request completed, `checkAndRequestRoles()` was called — and it was an empty method. The `showRoleSetup` variable was never updated, so the compose UI never recomposed.

### Impact
- After granting the default dialer or SMS role, the user remained stuck on the setup screen
- Had to restart the app to see the main navigation

### Files Changed

#### `app/.../MainActivity.kt`
**Before:** `showRoleSetup` was a local `remember` variable inside `setContent`.
**After:** `showRoleSetup` is a class-level `mutableStateOf<Boolean>` that is updated in:
- `roleRequestLauncher` callback (after role grant/deny)
- `onStart()` (re-checks on every resume, catches system settings changes)
- `onCreate()` (initial check)

```kotlin
private var showRoleSetup = mutableStateOf(false)

private val roleRequestLauncher = registerForActivityResult(...) { _ ->
    showRoleSetup.value = !roleManager.isFullyDefault()
}

override fun onStart() {
    super.onStart()
    showRoleSetup.value = !roleManager.isFullyDefault()
}
```

## Issue 3: Incoming SMS Silently Dropped

### Root Cause
`SmsReceiver` received `SMS_RECEIVED_ACTION` and forwarded data via a custom broadcast `ACTION_SMS_PROCESSED`, but no component was registered to receive that broadcast. The broadcast was sent into the void. `MessagingEngine.onIncomingSms()` was never called.

### Impact
- Incoming SMS were never stored in the database
- No events were emitted for incoming messages
- The messages/conversations screen was always empty for received messages

### Files Changed

#### `platform/.../SmsReceiver.kt`
**Before:** Sent `ACTION_SMS_PROCESSED` broadcast with message data.
**After:** Directly calls `MessagingEngine.onIncomingSms()` via Hilt `PlatformEntryPoint`:
- Uses `EntryPointAccessors.fromApplication()` to get `MessagingEngine` and `DeviceEngine`
- Processes messages in a `CoroutineScope` on `Dispatchers.IO`
- Properly logs success/failure

```kotlin
val entryPoint = EntryPointAccessors.fromApplication(
    context.applicationContext, PlatformEntryPoint::class.java
)
val messagingEngine = entryPoint.messagingEngine()
val deviceEngine = entryPoint.deviceEngine()

scope.launch {
    val deviceId = deviceEngine.getLocalDeviceId()
    messagingEngine.onIncomingSms(
        sender = sender, body = body, deviceId = deviceId,
        timestamp = timestamp, subscriptionId = subscriptionId
    )
}
```

## Issue 4: Build Errors

### Error 1: Duplicate `ApiRoutes` Class
**Symptom:** `:server:kspDebugKotlin` failed with compilation error.
**Cause:** `ApiRoutes` was defined in both `ApiServer.kt` and `ApiRoutes.kt` (same package).
**Fix:** Removed the duplicate from `ApiServer.kt`. The canonical definition in `ApiRoutes.kt` has `@Singleton` for Hilt DI.

### Error 2: Missing Serialization in UI Module
**Symptom:** `:ui:compileDebugKotlin` failed with "Unresolved reference 'serialization'" and "Unresolved reference 'JsonPrimitive'".
**Cause:** `TestingDashboardViewModel.kt` imported `kotlinx.serialization.json.JsonPrimitive` but the `ui` module was missing the serialization plugin and dependency.
**Fix:** Added `alias(libs.plugins.kotlin.serialization)` plugin and `implementation(libs.kotlinx.serialization.json)` dependency to `ui/build.gradle.kts`.

## Known Remaining Issues

### Call ID Mismatch
When `CallEngine.makeCall()` creates a record with callId `call_abc`, and the Telecom framework routes through `ConnectionService` which generates callId `call_xyz`, these are not linked. State transitions from the ConnectionService callbacks reference the wrong ID.

**Suggested fix:** Have `ConnectionService.onCreateOutgoingConnection()` look up the most recent outbound call record by phone number instead of generating a new ID.

### InCallService answerCall State Check
`InCallService.handleStateChange()` calls `callEngine.answerCall()` on `STATE_ACTIVE`, but `answerCall()` checks `entity.state != CallState.RINGING`. If the call state was already updated to `DIALING` by `makeCall()`, this check fails.

**Suggested fix:** Allow `answerCall()` to transition from `DIALING` or `RINGING` states.
